# WinMirroring — архитектура и план

Дата: 2026-11-07. Статус: предложение, до начала разработки.

## 1. Цель

Одно приложение на C#, которое превращает три Windows-устройства (ПК, ноутбук, планшет) в единое рабочее место:

| Фича | Что должно работать |
|---|---|
| Перенос ввода | Курсор переходит через край экрана на соседнее устройство, клавиатура следует за курсором (как Mouse Without Borders) |
| Перенос звука | Звук устройства, которым управляем, играет на устройстве, за которым сидим (та же логика «следует за фокусом ввода») |
| Файлы | Общий буфер обмена (текст, картинки, файлы) и drag & drop через край экрана |
| Экран | Окно с живым экраном другого устройства и управлением с него (в первую очередь ПК на планшете, с тачем) |
| Сеть | Только локальная сеть; пользователь выбирает интерфейсы/подсети, чтобы работало и через VPN |

Все устройства равноправны: на каждом стоит одно и то же приложение, выделенного сервера нет.

## 2. Почему не готовое

На 2026-11 ни один бесплатный продукт не закрывает все пять пунктов:

- PowerToys Mouse Without Borders: ввод + буфер + файлы через буфер (лимит ~100 МБ). Нет звука и экрана.
- Deskflow 1.27 / Input Leap: ввод + буфер. Нет файлов, звука, экрана.
- Hydra (новый, март 2026, GPL): ввод + буфер + файлы. Нет звука и экрана, не обкатан.
- Sunshine + Moonlight: экран + звук + удалённое управление, но это «стриминг игры», а не бесшовный KVM.
- Parsec: то же, закрытый, требует облачный аккаунт.
- RDP: блокирует консольную сессию, для зеркалирования не годится.

Покрыть всё можно только связкой из трёх-четырёх программ с разной логикой подключения и настроек. Поэтому пишем своё.

## 3. Стек

- .NET 10 (LTS), C# 14, TFM `net10.0-windows10.0.22621.0` (даёт проекции WinRT: Windows.Graphics.Capture и т.д.).
- UI: WPF. Причины: зрелый, лёгкий трей-апп, нормальный тач, можно хостить Direct3D-поверхность через HwndHost без лишних копий кадра. WinUI 3 красивее, но тяжелее в упаковке и отладке; переход возможен позже, ядро от UI не зависит.
- Win32 interop: `Microsoft.Windows.CsWin32` (генератор P/Invoke из метаданных, без ручных DllImport).
- Графика и медиа: `Vortice.Windows` (Direct3D11, DXGI, Media Foundation).
- Аудио: `NAudio` (WASAPI loopback/render), кодек Opus через `Concentus` (чистый C#, без нативных зависимостей).
- Сериализация управляющих сообщений: JSON (System.Text.Json) с дискриминатором типа `t` — их мало, зато читаются в логах; горячие пути (ввод, медиа) — фиксированные бинарные структуры.
- Логи: Serilog в файл с ротацией.

## 4. Сеть и безопасность

**Обнаружение.** Свой UDP-маячок (multicast + broadcast) на каждом выбранном интерфейсе. Через VPN (WireGuard, Tailscale, ZeroTier) broadcast обычно не ходит, поэтому дополнительно: ручной ввод адреса и список «запомненных» адресов пиров. Выбор интерфейсов/подсетей — отдельная настройка, слушатели биндятся только на выбранные адреса, никогда на 0.0.0.0.

**Транспорт.**

| Канал | Протокол | Зачем так |
|---|---|---|
| Управление, ввод, буфер обмена | TCP + TLS 1.3, одно мультиплексированное соединение, кадры с префиксом длины | Надёжность и порядок важнее, в LAN задержка TCP достаточна (MWB и Synergy тоже на TCP) |
| Файлы | Отдельное TCP + TLS соединение на передачу | Чтобы большой файл не блокировал ввод |
| Звук, видео | UDP, пакеты с seq/timestamp, шифрование AES-GCM ключом, выданным через TLS-канал | Потерянный кадр дешевле, чем ожидание ретрансмита |

QUIC (System.Net.Quic) рассматривался как единый транспорт, но в .NET нет API datagram, а выигрыш в LAN минимален. WebRTC — избыточен.

**Доверие.** У каждого устройства свой самоподписанный ECDSA-сертификат в хранилище CurrentUser\My (SChannel не принимает эфемерные ключи для TLS-сервера). TLS аутентифицирует только сервер; клиент доказывает свою личность уже внутри туннеля, подписывая случайный вызов сервера ключом своего сертификата (`PeerHandshake`). Сопряжение (протокол v3, по просьбе пользователя без ввода PIN): инициатор отправляет запрос, на отвечающем устройстве пользователь нажимает «Принять», после чего обе стороны закрепляют отпечаток сертификата друг друга (pinning). Сертификаты обеих сторон уже доказаны рукопожатием, поэтому сопряжение — это только решение пользователя доверять. Оба устройства показывают одинаковый шестизначный код подтверждения, вычисленный из обоих отпечатков (`PairingCrypto.ConfirmationCode`); его не вводят, а сравнивают взглядом. Непарные устройства видны в списке, но могут только запросить сопряжение.

Известное ограничение: если в момент сопряжения в сети сидит активный посредник, а пользователь нажмёт «Принять», не сравнив коды, посредник станет доверенным. Для домашней сети это принято осознанно в обмен на сопряжение одной кнопкой; сравнение кодов закрывает эту дыру для внимательного пользователя.

## 5. Модули

### 5.1 Ввод (WinMirroring.Input)

- Захват на устройстве, у которого физическая мышь/клавиатура: низкоуровневые хуки `WH_MOUSE_LL` и `WH_KEYBOARD_LL` на потоке с message loop; в «удалённом» режиме события проглатываются (возврат 1). Относительные дельты мыши берём через Raw Input (`WM_INPUT`), а не из координат курсора, чтобы не терять точность при упоре в край.
- Инъекция на принимающей стороне: `SendInput`. Клавиши передаём скан-кодами (`KEYEVENTF_SCANCODE`), чтобы не зависеть от раскладки; синхронизируем состояние модификаторов при переходе и сбрасываем их при разрыве связи.
- Раскладка устройств: пользователь расставляет устройства на 2D-сетке в UI. Края считаются по объединению прямоугольников мониторов каждого устройства (мультимонитор учитывается). Горячая клавиша «вернуть управление домой».
- Переход вместе со звуком и фокусом клавиатуры: событие `FocusChanged(deviceId)` — единая точка, на которую подписаны аудио и буфер.
- Ограничение UIPI: процесс средней целостности не может слать ввод в окна с повышенными правами (UAC, admin-приложения). Этап 1: опция «запускать с правами администратора». Позже: служба Windows + помощник в сессии пользователя (как MWB «service mode»), чтобы работали экран блокировки и UAC.

### 5.2 Звук (WinMirroring.Audio)

- Захват: WASAPI loopback с выбранного render-устройства (не обязательно default). Рендер: WASAPI shared, event-driven, буфер 10–20 мс. Джиттер-буфер на приёме с адаптивной целью 20–40 мс.
- Кодек: по умолчанию PCM 48 кГц 16 бит стерео (~1,5 Мбит/с, для LAN ничто), Opus 128–256 кбит/с для Wi-Fi/VPN. Переключается в настройках.
- Логика: «звук следует за фокусом ввода» плюс ручное закрепление («всегда гнать звук ноутбука на ПК»).
- Подводный камень: loopback берёт микс после регулятора громкости устройства, так что mute на источнике, как правило, глушит и loopback. Чтобы источник молчал локально, варианты: (а) вывод на endpoint без динамиков (HDMI монитора, S/PDIF), приложение само переключает default-устройство на время сессии и возвращает обратно; (б) process-loopback API Windows 11 (`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, режим «все процессы кроме своего») — проверить в прототипе, зависит ли от mute; (в) виртуальный аудиокабель (драйвер ядра, на C# не пишется, только как внешняя опция).

### 5.3 Буфер обмена и файлы (WinMirroring.Clipboard, WinMirroring.Files)

- Слушатель `AddClipboardFormatListener` → `WM_CLIPBOARDUPDATE`. Текст, HTML, картинки (PNG/DIB) до настраиваемого лимита отправляются сразу; для файлов (`CF_HDROP`) уходят только метаданные.
- Вставка файлов, этап 1 (как в MWB): при `Ctrl+V` на приёмнике файлы докачиваются в локальный кэш, затем в буфер кладётся `CF_HDROP` с путями кэша. Работает везде, цена — ожидание перед вставкой.
- Вставка файлов, этап 2: виртуальные файлы через свой `IDataObject` с `CFSTR_FILEDESCRIPTORW` / `CFSTR_FILECONTENTS` и отложенным рендерингом — Explorer тянет байты по сети прямо в момент вставки.
- Drag & drop через край: на источнике при переходе с зажатой кнопкой под курсором у края появляется прозрачное окно-`IDropTarget`, оно получает перетаскиваемый `IDataObject` и список файлов; на приёмнике запускается свой `DoDragDrop` с прокси-объектом, реальные байты стримятся при drop.
- Передача файлов: чанки 256 КБ – 1 МБ, хэш на чанк, докачка, прогресс в UI, ограничение скорости по желанию.

### 5.4 Экран (WinMirroring.Screen)

- Захват: Windows.Graphics.Capture по монитору (или окну), кадр приходит как D3D11-текстура, курсор рисуется самим WGC.
- Кодирование: Media Foundation H.264 encoder MFT с аппаратным ускорением (NVENC на GTX 1650, AMD VCE, Intel QSV — все через MF), 30–60 fps, 10–30 Мбит/с в LAN, программный fallback. Текстура не покидает GPU до энкодера.
- Декодирование: MF H.264 decoder с D3D11/DXVA, вывод в swap chain внутри `HwndHost` в окне WPF — без копий через managed-память.
- Управление с планшета: тап = клик, долгое нажатие = правая кнопка, два пальца = скролл, щипок = зум окна просмотра; перо — через `InjectSyntheticPointerInput` с давлением. Ввод идёт тем же каналом, что и в 5.1, но в «абсолютных» координатах.
- Звук в этом режиме стримится тем же модулем 5.2.

### 5.5 Приложение (WinMirroring.App)

- Трей-иконка, автозапуск, окно настроек: устройства и сопряжение, раскладка на сетке, интерфейсы/подсети, звук, буфер, горячие клавиши.
- Окно просмотра экрана — отдельное, полноэкранное на планшете.
- Один процесс на устройство. Служба Windows для UAC/экрана блокировки — отдельный этап.

## 7. Этапы и критерии готовности

| Этап | Содержание | Готово, когда |
|---|---|---|
| 0 | Окружение, каркас решения, Directory.Build.props, CI-сборка `dotnet build` | Пустое приложение собирается и висит в трее |
| 1 | Ядро: обнаружение, выбор интерфейсов, сопряжение подтверждением, TLS-канал, настройки | Два устройства видят друг друга, спариваются, показывают «подключено», переживают переподключение |
| 2 | Ввод: раскладка, края, хуки, SendInput, горячие клавиши, модификаторы | Управление тремя устройствами одной мышью и клавиатурой без залипаний |
| 3 | Буфер обмена: текст, картинки, файлы через кэш | Ctrl+C на одном, Ctrl+V на другом, включая файлы |
| 4 | Звук: loopback → PCM/Opus → рендер, следует за фокусом | Звук ноутбука в наушниках ПК с задержкой < 50 мс без щелчков |
| 5 | Экран: WGC + MF H.264 + тач-управление. Плюс трансляция одного окна или его части на другое устройство (тот же поток с фильтром по окну и обрезкой) | Планшет показывает ПК при 30–60 fps с задержкой < 100 мс в LAN; окно, отправленное на другое устройство, открывается там отдельным окном с управлением |
| 6 | Drag & drop через край, виртуальные файлы при вставке, служба для UAC/экрана блокировки, полировка DPI и мультимонитора | Повседневное использование без обходных путей |

Этапы 3 и 4 независимы друг от друга и от 5, их можно вести параллельно после этапа 2.

## 8. Риски и открытые вопросы

- Тихий звук на источнике без драйвера (см. 5.2) — проверяется прототипом на этапе 4.
- UAC/экран блокировки требуют службу и помощник с UIAccess; до этапа 6 ввод в такие окна не попадает.
- Аппаратный энкодер на планшете может отсутствовать — нужен программный fallback и настройка качества.
- Broadcast через VPN не ходит — ручные адреса обязательны с этапа 1.
- Антивирусы могут ругаться на глобальные хуки и SendInput; подпись сборок желательна.

## 10. Состояние

- Этапы 0–1 реализованы: `WinMirroring.Core` (обнаружение, TLS, рукопожатие, сопряжение, сессии), `WinMirroring.App` (трей, вкладки «Устройства», «Сеть», «Настройки», окна сопряжения), `wm-cli`, 40 тестов, включая интеграцию двух узлов на loopback.
- Этап 2 реализован в `WinMirroring.Input`: поток с хуками `WH_MOUSE_LL`/`WH_KEYBOARD_LL` и окном Raw Input, `InputInjector` на SendInput, бинарный кодек канала Input, раскладка-сетка с синхронизацией через `LayoutMessage`, `InputSharingService` с переходами через края в обе стороны, возвратом по Ctrl+Alt+Home и отпусканием зажатых клавиш при обрыве. В приложении вкладка «Раскладка» и индикатор «где ввод».
- Отличия от плана: движение мыши берётся из Raw Input (а не из координат хука), потому что у края экрана координаты зажаты и дельты теряются; инъекция движения абсолютная, чтобы не накладывать ускорение указателя дважды; injected-события (hDevice = 0) не считаются физическими, иначе управляемое устройство само пыталось бы перейти к соседу.
- Доработка этапа 2 по итогам проверки на устройствах (протокол v2):
  - Дёрганое движение. Причины: на управляемой стороне позиция бралась из GetCursorPos сразу после SendInput и отставала, а движение шло в сырых отсчётах мыши без ускорения. Теперь управляющий берёт смещение из `pt` низкоуровневого хука относительно припаркованного курсора (скорость и ускорение указателя уже применены), курсор паркуется в центре основного монитора под почти прозрачным окном-щитом с пустым курсором. Управляемая сторона ведёт свою позицию (`RemoteCursorPlayer`) и сверяется с системой только после 150 мс простоя.
  - Компенсация сети: каждое движение несёт метку времени управляющего в микросекундах, `PlayoutScheduler` оценивает минимальную задержку и пиковый разброс над ней и проигрывает движение с исходными интервалами на отдельном потоке с таймером высокого разрешения. Буфер адаптивный, ограничен настройкой (по умолчанию 30 мс). Клики и клавиши сначала доигрывают накопленное движение, чтобы попадать в нужную точку.
  - Блокировка ввода при обрыве. Причина: поток-обработчик ждал записи в сокет, а мёртвое соединение замечалось только через тайм-аут TCP или heartbeat. Теперь отправка идёт через буфер `InputSender` и никогда не блокирует хуки; захват — это аренда, которую управляемая сторона продлевает keepalive каждые 250 мс. Без ответа 1,5 с хук сам отпускает ввод при следующем событии. Управляемая сторона без вестей 2 с отпускает зажатые клавиши. На сокетах включены TCP keepalive и TCP_MAXRT = 10 с.
  - Приложение: контекстное меню устройства, колонка задержки, прикладной пинг (`PeerSession.PingAsync`), настройки сглаживания.
- Не проверено на двух физических устройствах после доработки.
- Этап 3 реализован в `WinMirroring.Clipboard` (отдельного проекта Files нет, передача файлов живёт там же):
  - STA-поток с окном-слушателем `AddClipboardFormatListener`, задержка 150 мс на «успокоение» буфера, свои записи отсекаются по `GetClipboardSequenceNumber`, поэтому эха между устройствами нет.
  - Форматы: CF_UNICODETEXT, HTML Format, Rich Text Format, PNG, CF_DIB, сырыми байтами, сжатие zlib выше 8 КБ. Сообщения до 256 КБ идут в канале Clipboard целиком, крупнее — ссылкой, которую получатель вытягивает через канал File окном из 3 запросов по 128 КБ. Это ограничивает объём данных в полёте и не даёт большому скриншоту задержать мышь.
  - Файлы: источник хранит последние 8 предложений (раскрытые рекурсивно, без reparse-точек, до 50 000 записей) и отдаёт только их по паре «предложение, индекс». Получатель кладёт в буфер свой COM `IDataObject` (`VirtualFileDataObject`) с `FileGroupDescriptorW` + `FileContents` (IStream с упреждающим чтением), плюс `CF_HDROP` с докачкой в кэш для наборов до 64 МБ. Пути из чужого предложения проверяются: только относительные, без `..`, дисков и запрещённых символов.
- Этап 4 реализован в `WinMirroring.Audio` на NAudio 3.3 (новые `WasapiRecorderBuilder`/`WasapiPlayerBuilder`) и Concentus 2.2 (Opus на C#):
  - Проверено опытом на Windows 11: и endpoint loopback, и process loopback не зависят от mute устройства (уровень тестового тона одинаков с mute и без). Поэтому локальные динамики глушатся на время передачи, флаг «заглушено нами» хранится в настройках и снимается при следующем запуске, если приложение упало.
  - Захват: process loopback в режиме ExcludeTargetProcessTree для своего процесса, сразу 48 кГц float stereo. Это убирает эхо-петлю: принятый звук играет в нашем процессе и в захват не попадает. Запасной путь: endpoint loopback в формате микшера с пересэмплированием WDL; пока устройство само воспроизводит чужой звук, передача приостанавливается.
  - Транспорт: UDP-сокет на номере транспортного порта (`MediaSocket` в Core), пакеты AES-256-GCM (`MediaCipher`), ключ на поток в `AudioStartMessage` внутри TLS. Источник пакета сверяется с адресом сессии. Долгая цифровая тишина не отправляется.
  - Приём: Opus с маскировкой потерь до 5 кадров, джиттер-буфер на поток (старт после набора цели, перебуферизация после провала, обрезка до цели при росте больше чем на 60 мс), микшер NAudio, общий выход WASAPI с задержкой 20 мс.
  - Маршрут: «звук следует за вводом» через событие `InputSharingService.ControlledByChanged`, либо закреплённый получатель. Остановка с задержкой 2 с.
- Не проверено на двух физических устройствах: буфер обмена и звук между ноутбуком и планшетом. Живой буфер в тестах не трогается, чтобы не портить содержимое буфера на машине разработки. Проверены кодеки, COM-объект, сквозная передача файла по реальной TLS-сессии, цепочка Opus/AES-GCM, джиттер-буфер и живой захват звука (process loopback выдаёт кадры в реальном времени).
- Drag & drop файлов (часть этапа 6, сделан раньше):
  - Поверхность (`DragSurface`, почти прозрачное окно поверх всех на STA-потоке буфера, зарегистрированное через `RegisterDragDrop`) работает в двух ролях: ловушка — стоит под курсором во время чужого перетаскивания и узнаёт, что тащат (CF_HDROP, либо наш собственный `VirtualFileDataObject`, который передаётся дальше без изменений), но бросок не принимает; точка старта — стоит под курсором, когда мы сами нажимаем кнопку перед `DoDragDrop`, чтобы это нажатие не кликнуло по чужому окну.
  - Наружу с управляющего: захват к соседу начался при зажатой левой кнопке → ловушка под припаркованным курсором + сдвиг курсора на пиксель (чтобы цикл перетаскивания заметил новое окно) → сосед получает `DragStart` и запускает у себя `DoDragDrop` с виртуальными файлами, кнопка «нажимается» как отслеживаемая, поэтому при уходе управления сначала отменяется перетаскивание, потом отпускаются кнопки. Физическое отпускание на управляющем уходит соседу (бросок там) и проходит локально на ловушку (исходное перетаскивание в Explorer завершается без эффекта).
  - Наружу с управляемого: курсор упирается в край при зажатой кнопке → `BeforeEdgeHandOff` (до 1 с) ловит перетаскивание у края и отправляет управляющему `DragOut` раньше, чем `EdgeReached`; сообщения перетаскивания обрабатываются в потоке приёма синхронно, поэтому порядок гарантирован. Когда курсор садится на управляющего, там стартует локальное перетаскивание; если на третье устройство — ему уходит `DragStart` с исходным источником файлов.
  - Содержимое всегда тянется с устройства-владельца файлов по каналу File, как при вставке.
  - Не проверено вживую: на машине разработки нельзя нажимать мышь за пользователя. Проверены кодеки сообщений и создание поверхности.
- Этап 5 реализован в `WinMirroring.Screen` (Vortice.Direct3D11/DXGI, WIC из Vortice.Direct2D1, WinRT-проекции из TFM):
  - Отличие от плана: вместо аппаратного H.264 через Media Foundation — плитки 128×128, сравнение с прошлым кадром и JPEG (WIC, параллельно по ядрам) только для изменившихся. Прототип на ноутбуке: считывание кадра 1080p ~4,5 мс, кодирование полного кадра ~5 мс на 12 ядрах (231 КБ при качестве 0,7). Для рабочего стола и окон это даёт малую задержку без инфраструктуры MFT/NV12/DXVA; для полноэкранного видео H.264 лучше и остаётся следующим шагом (кодировщик изолирован в `TileEncoder`).
  - Захват: `WgcCapture` (Windows.Graphics.Capture через `IGraphicsCaptureItemInterop`) для монитора или окна, окно захватывается даже перекрытым; рамка захвата отключена; кадр копируется в staging-текстуру и читается в управляемый буфер, потребитель берёт последний кадр, лишние пропускаются.
  - Транспорт: канал Screen той же TLS-сессии. Не больше двух неподтверждённых сообщений кадра, части до 512 КБ; просмотрщик подтверждает кадр только после того, как UI его отрисовал, поэтому частота кадров сама подстраивается под сеть и скорость отрисовки, а очередь не растёт. Управляющие сообщения `ScreenRequest`/`ScreenStream`/`ScreenStop` в канале Control.
  - Управление из просмотрщика: указатель в нормированных координатах изображения, клавиши по VK и скан-коду, источник пересчитывает их через обрезку и границы монитора/окна в физические пиксели и вводит отдельным `InputInjector` (его кнопки отпускаются при остановке потока). Для окна перед нажатием оно выводится на передний план.
  - Окно на другое устройство: из меню устройства (выбор окна) или перетаскиванием за заголовок через край экрана (`WindowDragWatcher` на WinEvent move/size; в момент ухода курсора на соседа при зажатой кнопке окно отправляется туда и после окончания перемещения возвращается на исходное место). Часть окна — обрезка, которую задаёт просмотрщик рамкой.
  - Проверено: кодек и плитки, пересчёт координат, сквозной поток монитора между двумя узлами по TLS на loopback с совпадением изображения с прямым захватом (средняя ошибка в пределах JPEG). Не проверено вживую: окно просмотра на втором устройстве, управление с планшета касаниями, перетаскивание окна.
- Сопряжение без PIN (протокол v3): оба устройства показывают код подтверждения, вычисленный из сертификатов, на втором устройстве только кнопка «Принять».
- Доработка по итогам проверки ноутбук ↔ планшет:
  - Буфер обмена и перетаскивание файлов. Живые тесты на ноутбуке (два `ClipboardThread`, затем два узла по TLS с `ClipboardSyncService`) нашли ошибку: классы окон регистрировались под общими именами, и второй экземпляр получал WndProc первого. Имена классов теперь уникальны на экземпляр (буфер, поверхность перетаскивания, окна хуков ввода). В журнале ноутбука видно, что буфер и `DragStart` уходили на планшет, а подтверждений обработки нет; вероятнее всего, на планшете при старте падал запуск буфера обмена, который был в одном блоке с перетаскиванием. Теперь каждая функция запускается отдельно через `FeatureHealth` (результат на вкладке «Настройки» и уведомлением), поверхность перетаскивания необязательна для буфера, а журнал любого сопряжённого устройства можно получить по сессии (`LogRequest`/`LogResponse`, `DiagnosticsService`, последние 2 МБ).
  - Гонка при сопряжении: инициатор переходил в Ready раньше, чем ответчик сохранял сопряжение, и первые сообщения (раскладка) терялись. Теперь ответчик сохраняет, отвечает `PairResult` и только потом становится Ready, а инициатор сохраняет и становится Ready по получении ответа.
  - Звук только в одну сторону: маршрут знал только «следует за вводом». Добавлены «следует за просмотром экрана» (`ScreenStreamingService.ViewersChanged`), запрос «слушать здесь» (`AudioRouteRequest`) и закреплённый получатель из меню устройства.
  - Перетаскивание окна в обе стороны: на управляемом устройстве окно, которое тянут за заголовок, при уходе курсора к управляющему отправляется ему (`TrySendMovingWindowAsync` в `BeforeEdgeHandOff`), а ловушка файлов в это время не ставится. Повторные потоки одного окна одному устройству больше не создаются.
  - Окно просмотра: касания передаются сообщением `Touch` и вводятся на источнике через `InjectTouchInput` (до 10 контактов, keepalive 50 мс, отпускание при остановке потока); символы без клавиши — сообщением `Text` (KEYEVENTF_UNICODE); кнопка экранной клавиатуры (`ITipInvocation`, запасной вариант osk.exe); отпускание кнопки без нажатия в этом окне игнорируется, при потере фокуса окна всё нажатое там отпускается.
  - Файлы через окно просмотра (канал Clipboard, сообщения 6–8): бросок в окно — источник ставит курсор в точку, кладёт поверхность-старт, сам нажимает кнопку, запускает `DoDragDrop` с виртуальными файлами, убирает поверхность, шевелит курсор и отпускает кнопку над окном в этой точке. Вытягивание из окна — когда курсор с зажатой кнопкой уходит за край изображения, просмотрщик просит источник поймать перетаскивание в последней точке, завершает его там (бросок на ловушку без эффекта) и запускает то же перетаскивание у себя.
  - Не проверено вживую на двух устройствах; проверены кодеки новых сообщений и сборка.
- Вторая проверка на планшете:
  - Потеря курсора. Причина: при активном окне администратора UIPI молча отбрасывает SendInput, а `RemoteCursorPlayer` после 150 мс простоя принимал застрявшую системную позицию за свою, поэтому дойти до края и вернуться было нельзя. Теперь при расхождении позиций проверяется уровень целостности процесса активного окна (`InjectionGuard`): если он выше нашего, отслеживаемая позиция сохраняется, края работают, управляющему уходит `InputBlocked` с заголовком окна (уведомление), то же для управления из окна просмотра. Если Windows скрыла курсор после касаний (CURSOR_SUPPRESSED), относительный сдвиг на пиксель возвращает его.
  - «Вернуть курсор» на управляемом устройстве: перестаёт исполнять ввод и шлёт `InputReleaseRequest`, управляющий завершает захват. Работает и со старой версией на управляющем: без keepalive его аренда истекает за 1,5 с.
  - Перезапуск с правами администратора (UAC, новый экземпляр ждёт мьютекс до 20 с). Цена: UIPI не пускает перетаскивание из обычного Explorer в повышенный процесс и вызовы COM к нашему объекту с виртуальными файлами, поэтому на таком устройстве не работают перетаскивание файлов из Explorer и вставка файлов с других устройств. Правильное решение — отдельный повышенный помощник или служба только для инъекции ввода (этап 6), с осторожностью: такой помощник фактически даёт обычным процессам пользователя ввод в окна администратора.
  - Окно просмотра: полноэкранный режим с кнопкой-ручкой сверху вместо F11, правая панель быстрых параметров (окно, управление, курсор, звук, изображение, буфер), уведомления поверх изображения. Меню значка в трее с теми же быстрыми действиями.
