# WinMirroring — архитектура и план

Дата: 2026-11-07. Статус: предложение, до начала разработки.

## 1. Цель

Одно приложение на C#, которое превращает три Windows-устройства (ПК, ноутбук, планшет) в единое рабочее место:

| Фича | Что должно работать |
|---|---|
| Перенос ввода | Курсор переходит через край экрана на соседнее устройство, клавиатура следует за курсором (как Mouse Without Borders) |
| Перенос звука | Звук устройства, которым управляем, играет на устройстве, за которым сидим (та же логика «следует за фокусом ввода») |
| Файлы | Общий буфер обмена (текст, картинки, файлы) и drag & drop через край экрана |
| Экран | Окно с живым экраном другого устройства и управлением с него (в первую очередь ПК на планшете, с тачем) |
| Сеть | Только локальная сеть; пользователь выбирает интерфейсы/подсети, чтобы работало и через VPN |

Все устройства равноправны: на каждом стоит одно и то же приложение, выделенного сервера нет.

## 2. Почему не готовое

На 2026-11 ни один бесплатный продукт не закрывает все пять пунктов:

- PowerToys Mouse Without Borders: ввод + буфер + файлы через буфер (лимит ~100 МБ). Нет звука и экрана.
- Deskflow 1.27 / Input Leap: ввод + буфер. Нет файлов, звука, экрана.
- Hydra (новый, март 2026, GPL): ввод + буфер + файлы. Нет звука и экрана, не обкатан.
- Sunshine + Moonlight: экран + звук + удалённое управление, но это «стриминг игры», а не бесшовный KVM.
- Parsec: то же, закрытый, требует облачный аккаунт.
- RDP: блокирует консольную сессию, для зеркалирования не годится.

Покрыть всё можно только связкой из трёх-четырёх программ с разной логикой подключения и настроек. Поэтому пишем своё.

## 3. Стек

- .NET 10 (LTS), C# 14, TFM `net10.0-windows10.0.22621.0` (даёт проекции WinRT: Windows.Graphics.Capture и т.д.).
- UI: WPF. Причины: зрелый, лёгкий трей-апп, нормальный тач, можно хостить Direct3D-поверхность через HwndHost без лишних копий кадра. WinUI 3 красивее, но тяжелее в упаковке и отладке; переход возможен позже, ядро от UI не зависит.
- Win32 interop: `Microsoft.Windows.CsWin32` (генератор P/Invoke из метаданных, без ручных DllImport).
- Графика и медиа: `Vortice.Windows` (Direct3D11, DXGI, Media Foundation).
- Аудио: `NAudio` (WASAPI loopback/render), кодек Opus через `Concentus` (чистый C#, без нативных зависимостей).
- Сериализация управляющих сообщений: JSON (System.Text.Json) с дискриминатором типа `t` — их мало, зато читаются в логах; горячие пути (ввод, медиа) — фиксированные бинарные структуры.
- Логи: Serilog в файл с ротацией.

## 4. Сеть и безопасность

**Обнаружение.** Свой UDP-маячок (multicast + broadcast) на каждом выбранном интерфейсе. Через VPN (WireGuard, Tailscale, ZeroTier) broadcast обычно не ходит, поэтому дополнительно: ручной ввод адреса и список «запомненных» адресов пиров. Выбор интерфейсов/подсетей — отдельная настройка, слушатели биндятся только на выбранные адреса, никогда на 0.0.0.0.

**Транспорт.**

| Канал | Протокол | Зачем так |
|---|---|---|
| Управление, ввод, буфер обмена | TCP + TLS 1.3, одно мультиплексированное соединение, кадры с префиксом длины | Надёжность и порядок важнее, в LAN задержка TCP достаточна (MWB и Synergy тоже на TCP) |
| Файлы | Отдельное TCP + TLS соединение на передачу | Чтобы большой файл не блокировал ввод |
| Звук, видео | UDP, пакеты с seq/timestamp, шифрование AES-GCM ключом, выданным через TLS-канал | Потерянный кадр дешевле, чем ожидание ретрансмита |

QUIC (System.Net.Quic) рассматривался как единый транспорт, но в .NET нет API datagram, а выигрыш в LAN минимален. WebRTC — избыточен.

**Доверие.** У каждого устройства свой самоподписанный ECDSA-сертификат в хранилище CurrentUser\My (SChannel не принимает эфемерные ключи для TLS-сервера). TLS аутентифицирует только сервер; клиент доказывает свою личность уже внутри туннеля, подписывая случайный вызов сервера ключом своего сертификата (`PeerHandshake`). Сопряжение (протокол v3, по просьбе пользователя без ввода PIN): инициатор отправляет запрос, на отвечающем устройстве пользователь нажимает «Принять», после чего обе стороны закрепляют отпечаток сертификата друг друга (pinning). Сертификаты обеих сторон уже доказаны рукопожатием, поэтому сопряжение — это только решение пользователя доверять. Оба устройства показывают одинаковый шестизначный код подтверждения, вычисленный из обоих отпечатков (`PairingCrypto.ConfirmationCode`); его не вводят, а сравнивают взглядом. Непарные устройства видны в списке, но могут только запросить сопряжение.

Известное ограничение: если в момент сопряжения в сети сидит активный посредник, а пользователь нажмёт «Принять», не сравнив коды, посредник станет доверенным. Для домашней сети это принято осознанно в обмен на сопряжение одной кнопкой; сравнение кодов закрывает эту дыру для внимательного пользователя.

## 5. Модули

### 5.1 Ввод (WinMirroring.Input)

- Захват на устройстве, у которого физическая мышь/клавиатура: низкоуровневые хуки `WH_MOUSE_LL` и `WH_KEYBOARD_LL` на потоке с message loop; в «удалённом» режиме события проглатываются (возврат 1). Относительные дельты мыши берём через Raw Input (`WM_INPUT`), а не из координат курсора, чтобы не терять точность при упоре в край.
- Инъекция на принимающей стороне: `SendInput`. Клавиши передаём скан-кодами (`KEYEVENTF_SCANCODE`), поэтому символ определяет раскладка принимающего устройства; сама раскладка синхронизируется отдельным сообщением (раздел 10). Модификаторы синхронизируем при переходе и сбрасываем при разрыве связи.
- Раскладка устройств: пользователь расставляет устройства на 2D-сетке в UI. Края считаются по объединению прямоугольников мониторов каждого устройства (мультимонитор учитывается). Горячая клавиша «вернуть управление домой».
- Переход вместе со звуком и фокусом клавиатуры: событие `FocusChanged(deviceId)` — единая точка, на которую подписаны аудио и буфер.
- Ограничение UIPI: процесс средней целостности не может слать ввод в окна с повышенными правами (UAC, admin-приложения). Этап 1: опция «запускать с правами администратора». Позже: служба Windows + помощник в сессии пользователя (как MWB «service mode»), чтобы работали экран блокировки и UAC.

### 5.2 Звук (WinMirroring.Audio)

- Захват: WASAPI loopback с выбранного render-устройства (не обязательно default). Рендер: WASAPI shared, event-driven, буфер 10–20 мс. Джиттер-буфер на приёме с адаптивной целью 20–40 мс.
- Кодек: по умолчанию PCM 48 кГц 16 бит стерео (~1,5 Мбит/с, для LAN ничто), Opus 128–256 кбит/с для Wi-Fi/VPN. Переключается в настройках.
- Логика: «звук следует за фокусом ввода» плюс ручное закрепление («всегда гнать звук ноутбука на ПК»).
- Подводный камень: loopback берёт микс после регулятора громкости устройства, так что mute на источнике, как правило, глушит и loopback. Чтобы источник молчал локально, варианты: (а) вывод на endpoint без динамиков (HDMI монитора, S/PDIF), приложение само переключает default-устройство на время сессии и возвращает обратно; (б) process-loopback API Windows 11 (`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, режим «все процессы кроме своего») — проверить в прототипе, зависит ли от mute; (в) виртуальный аудиокабель (драйвер ядра, на C# не пишется, только как внешняя опция).

### 5.3 Буфер обмена и файлы (WinMirroring.Clipboard, WinMirroring.Files)

- Слушатель `AddClipboardFormatListener` → `WM_CLIPBOARDUPDATE`. Текст, HTML, картинки (PNG/DIB) до настраиваемого лимита отправляются сразу; для файлов (`CF_HDROP`) уходят только метаданные.
- Вставка файлов, этап 1 (как в MWB): при `Ctrl+V` на приёмнике файлы докачиваются в локальный кэш, затем в буфер кладётся `CF_HDROP` с путями кэша. Работает везде, цена — ожидание перед вставкой.
- Вставка файлов, этап 2: виртуальные файлы через свой `IDataObject` с `CFSTR_FILEDESCRIPTORW` / `CFSTR_FILECONTENTS` и отложенным рендерингом — Explorer тянет байты по сети прямо в момент вставки.
- Drag & drop через край: на источнике при переходе с зажатой кнопкой под курсором у края появляется прозрачное окно-`IDropTarget`, оно получает перетаскиваемый `IDataObject` и список файлов; на приёмнике запускается свой `DoDragDrop` с прокси-объектом, реальные байты стримятся при drop.
- Передача файлов: чанки 256 КБ – 1 МБ, хэш на чанк, докачка, прогресс в UI, ограничение скорости по желанию.

### 5.4 Экран (WinMirroring.Screen)

- Захват: Windows.Graphics.Capture по монитору (или окну), кадр приходит как D3D11-текстура, курсор рисуется самим WGC. Текстура считывается в управляемый BGRA-буфер (`WgcCapture.TryCopyLatest`); медленный получатель просто пропускает кадры.
- Кодирование — два пути, выбор по согласованию кодека (см. ниже):
  - **H.264 (аппаратный).** `H264VideoEncoder` поверх асинхронного Media Foundation encoder MFT (Vortice.MediaFoundation): перечисление с флагом `MFT_ENUM_FLAG_HARDWARE` (NVENC / AMD VCE / Intel QSV — все через MF), `MF_LOW_LATENCY`, по возможности CBR/без B-кадров/GOP через `ICodecAPI`. MFT'у передаётся D3D11 device manager (аппаратным кодерам он нужен даже для входа из системной памяти); MFT управляется отдельным потоком-насосом по событиям `METransformNeedInput`/`METransformHaveOutput`. Вход — NV12 (пока CPU-конвертация BGRA→NV12, `Nv12Converter`; подача GPU-текстуры без обратного чтения — следующий шаг). Выход — поток access unit'ов Annex-B с SPS/PPS в ключевых кадрах; ключевой кадр — на старте и при смене размера/обрезки (энкодер пересоздаётся), кадр-ключ детектируется по типам NAL (5/7).
  - **JPEG-плитки (fallback и выбор по умолчанию при отсутствии аппаратного H.264).** `TileEncoder`: разбивка на 128×128, сравнение с прошлым кадром, JPEG (WIC) только изменившихся плиток, параллельно по ядрам. Статичный рабочий стол — почти бесплатно.
- Декодирование: `H264VideoDecoder` поверх синхронного Microsoft H.264 decoder MFT (всегда есть в Windows, внутри использует DXVA), вход — Annex-B, выход — NV12 (через `IMF2DBuffer.ContiguousCopyTo`, что убирает выравнивание строк), затем CPU NV12→BGRA в тот же буфер изображения. Плитки декодируются `TileDecoder` (WIC) прямо в BGRA. Презентация — в `WriteableBitmap` окна WPF; кадр подтверждается только после отрисовки, поэтому частота кадров сама подстраивается. (Zero-copy через `D3DImage`/DXVA — следующий шаг.)
- Согласование кодека: при готовности сессии каждая сторона шлёт `ScreenCapabilityMessage(CanEncodeH264, CanDecodeH264)` (способность определяется реальной пробой создания MFT, кэшируется на процесс — `VideoCodecSupport`). Источник выбирает H.264, только если настройка это разрешает (`ScreenSettings.VideoCodec` = Auto/Jpeg/H264), он сам умеет кодировать и получатель заявил, что умеет декодировать; иначе — JPEG. Выбранный кодек объявляется в `ScreenStreamMessage.Codec`. Каждое сообщение канала самоописательно по типу (`Frame`/`VideoFrame`), поэтому получатель разбирает смешанный поток, а источник может «на лету» откатиться на JPEG (ошибка энкодера), и просмотрщик это переживёт.
- Управление с планшета: тап = клик, долгое нажатие = правая кнопка, два пальца = скролл, щипок = зум окна просмотра; перо — через `InjectSyntheticPointerInput` с давлением. Ввод идёт тем же каналом, что и в 5.1, но в «абсолютных» (нормализованных) координатах — независимо от кодека.
- Звук в этом режиме стримится тем же модулем 5.2.

### 5.5 Приложение (WinMirroring.App)

- Трей-иконка, автозапуск, окно настроек: устройства и сопряжение, раскладка на сетке, интерфейсы/подсети, звук, буфер, горячие клавиши.
- Окно просмотра экрана — отдельное, полноэкранное на планшете.
- Один процесс на устройство. Служба Windows для UAC/экрана блокировки — отдельный этап.

## 7. Этапы и критерии готовности

| Этап | Содержание | Готово, когда |
|---|---|---|
| 0 | Окружение, каркас решения, Directory.Build.props, CI-сборка `dotnet build` | Пустое приложение собирается и висит в трее |
| 1 | Ядро: обнаружение, выбор интерфейсов, сопряжение подтверждением, TLS-канал, настройки | Два устройства видят друг друга, спариваются, показывают «подключено», переживают переподключение |
| 2 | Ввод: раскладка, края, хуки, SendInput, горячие клавиши, модификаторы | Управление тремя устройствами одной мышью и клавиатурой без залипаний |
| 3 | Буфер обмена: текст, картинки, файлы через кэш | Ctrl+C на одном, Ctrl+V на другом, включая файлы |
| 4 | Звук: loopback → PCM/Opus → рендер, следует за фокусом | Звук ноутбука в наушниках ПК с задержкой < 50 мс без щелчков |
| 5 | Экран: WGC + MF H.264 + тач-управление. Плюс трансляция одного окна или его части на другое устройство (тот же поток с фильтром по окну и обрезкой) | Планшет показывает ПК при 30–60 fps с задержкой < 100 мс в LAN; окно, отправленное на другое устройство, открывается там отдельным окном с управлением |
| 6 | Drag & drop через край, виртуальные файлы при вставке, служба для UAC/экрана блокировки, полировка DPI и мультимонитора | Повседневное использование без обходных путей |

Этапы 3 и 4 независимы друг от друга и от 5, их можно вести параллельно после этапа 2.

## 8. Риски и открытые вопросы

- Тихий звук на источнике без драйвера (см. 5.2) — проверяется прототипом на этапе 4.
- UAC/экран блокировки требуют службу и помощник с UIAccess; до этапа 6 ввод в такие окна не попадает.
- Аппаратный энкодер на планшете может отсутствовать — нужен программный fallback и настройка качества.
- Broadcast через VPN не ходит — ручные адреса обязательны с этапа 1.
- Антивирусы могут ругаться на глобальные хуки и SendInput; подпись сборок желательна.

## 10. Состояние

- Этапы 0–1 реализованы: `WinMirroring.Core` (обнаружение, TLS, рукопожатие, сопряжение, сессии), `WinMirroring.App` (трей, вкладки «Устройства», «Сеть», «Настройки», окна сопряжения), `wm-cli`, 40 тестов, включая интеграцию двух узлов на loopback.
- Этап 2 реализован в `WinMirroring.Input`: поток с хуками `WH_MOUSE_LL`/`WH_KEYBOARD_LL` и окном Raw Input, `InputInjector` на SendInput, бинарный кодек канала Input, раскладка-сетка с синхронизацией через `LayoutMessage`, `InputSharingService` с переходами через края в обе стороны, возвратом по Ctrl+Alt+Home и отпусканием зажатых клавиш при обрыве. В приложении вкладка «Раскладка» и индикатор «где ввод».
- Отличия от плана: движение мыши берётся из Raw Input (а не из координат хука), потому что у края экрана координаты зажаты и дельты теряются; инъекция движения абсолютная, чтобы не накладывать ускорение указателя дважды; injected-события (hDevice = 0) не считаются физическими, иначе управляемое устройство само пыталось бы перейти к соседу.
- Доработка этапа 2 по итогам проверки на устройствах (протокол v2):
  - Дёрганое движение. Причины: на управляемой стороне позиция бралась из GetCursorPos сразу после SendInput и отставала, а движение шло в сырых отсчётах мыши без ускорения. Теперь управляющий берёт смещение из `pt` низкоуровневого хука относительно припаркованного курсора (скорость и ускорение указателя уже применены), курсор паркуется в центре основного монитора под почти прозрачным окном-щитом с пустым курсором. Управляемая сторона ведёт свою позицию (`RemoteCursorPlayer`) и сверяется с системой только после 150 мс простоя.
  - Компенсация сети: каждое движение несёт метку времени управляющего в микросекундах, `PlayoutScheduler` оценивает минимальную задержку и пиковый разброс над ней и проигрывает движение с исходными интервалами на отдельном потоке с таймером высокого разрешения. Буфер адаптивный, ограничен настройкой (по умолчанию 30 мс). Клики и клавиши сначала доигрывают накопленное движение, чтобы попадать в нужную точку.
  - Блокировка ввода при обрыве. Причина: поток-обработчик ждал записи в сокет, а мёртвое соединение замечалось только через тайм-аут TCP или heartbeat. Теперь отправка идёт через буфер `InputSender` и никогда не блокирует хуки; захват — это аренда, которую управляемая сторона продлевает keepalive каждые 250 мс. Без ответа 1,5 с хук сам отпускает ввод при следующем событии. Управляемая сторона без вестей 2 с отпускает зажатые клавиши. На сокетах включены TCP keepalive и TCP_MAXRT = 10 с.
  - Приложение: контекстное меню устройства, колонка задержки, прикладной пинг (`PeerSession.PingAsync`), настройки сглаживания.
- Не проверено на двух физических устройствах после доработки.

- Drag & drop файлов (часть этапа 6, сделан раньше):
  - Поверхность (`DragSurface`, почти прозрачное окно поверх всех на STA-потоке буфера, зарегистрированное через `RegisterDragDrop`) работает в двух ролях: ловушка — стоит под курсором во время чужого перетаскивания и узнаёт, что тащат (CF_HDROP, либо наш собственный `VirtualFileDataObject`, который передаётся дальше без изменений), но бросок не принимает; точка старта — стоит под курсором, когда мы сами нажимаем кнопку перед `DoDragDrop`, чтобы это нажатие не кликнуло по чужому окну.
  - Наружу с управляющего: захват к соседу начался при зажатой левой кнопке → ловушка под припаркованным курсором + сдвиг курсора на пиксель (чтобы цикл перетаскивания заметил новое окно) → сосед получает `DragStart` и запускает у себя `DoDragDrop` с виртуальными файлами, кнопка «нажимается» как отслеживаемая, поэтому при уходе управления сначала отменяется перетаскивание, потом отпускаются кнопки. Физическое отпускание на управляющем уходит соседу (бросок там) и проходит локально на ловушку (исходное перетаскивание в Explorer завершается без эффекта).
  - Наружу с управляемого: курсор упирается в край при зажатой кнопке → `BeforeEdgeHandOff` (до 1 с) ловит перетаскивание у края и отправляет управляющему `DragOut` раньше, чем `EdgeReached`; сообщения перетаскивания обрабатываются в потоке приёма синхронно, поэтому порядок гарантирован. Когда курсор садится на управляющего, там стартует локальное перетаскивание; если на третье устройство — ему уходит `DragStart` с исходным источником файлов.
  - Содержимое всегда тянется с устройства-владельца файлов по каналу File, как при вставке.
  - Не проверено вживую: на машине разработки нельзя нажимать мышь за пользователя. Проверены кодеки сообщений и создание поверхности.

- Вторая проверка на планшете:
  - Потеря курсора. Причина: при активном окне администратора UIPI молча отбрасывает SendInput, а `RemoteCursorPlayer` после 150 мс простоя принимал застрявшую системную позицию за свою, поэтому дойти до края и вернуться было нельзя. Теперь при расхождении позиций проверяется уровень целостности процесса активного окна (`InjectionGuard`): если он выше нашего, отслеживаемая позиция сохраняется, края работают, управляющему уходит `InputBlocked` с заголовком окна (уведомление), то же для управления из окна просмотра. Если Windows скрыла курсор после касаний (CURSOR_SUPPRESSED), относительный сдвиг на пиксель возвращает его.
  - «Вернуть курсор» на управляемом устройстве: перестаёт исполнять ввод и шлёт `InputReleaseRequest`, управляющий завершает захват. Работает и со старой версией на управляющем: без keepalive его аренда истекает за 1,5 с.
  - Перезапуск с правами администратора (UAC, новый экземпляр ждёт мьютекс до 20 с). Цена: UIPI не пускает перетаскивание из обычного Explorer в повышенный процесс и вызовы COM к нашему объекту с виртуальными файлами, поэтому на таком устройстве не работают перетаскивание файлов из Explorer и вставка файлов с других устройств. Правильное решение — отдельный повышенный помощник или служба только для инъекции ввода (этап 6), с осторожностью: такой помощник фактически даёт обычным процессам пользователя ввод в окна администратора.
  - Окно просмотра: полноэкранный режим с кнопкой-ручкой сверху вместо F11, правая панель быстрых параметров (окно, управление, курсор, звук, изображение, буфер), уведомления поверх изображения. Меню значка в трее с теми же быстрыми действиями.
- Второй монитор (`ScreenStreamingService.Display`, `Display/VirtualDisplay`, `Display/VirtualDisplaySetup`):
  - Окно «как на дополнительный монитор» без драйвера невозможно: окно за пределами экрана можно транслировать, но мышь и касания туда не ввести. Поэтому используется открытый IddCx-драйвер Virtual Display Driver (MIT, подпись SignPath). Сверено по исходникам: канал `\\.\pipe\MTTVirtualDisplayPipe` (UTF-16, одна команда на соединение, доступ у всех) не умеет добавлять и убирать мониторы на лету, число мониторов и разрешения из `vdd_settings.xml` (`C:\VirtualDisplayDriver` или `HKLM\SOFTWARE\MikeTheTech\VirtualDisplayDriver\VDDPATH`) читаются только при старте устройства, 0 мониторов даёт 1.
  - Поэтому драйвер держит один монитор постоянно, а мы подключаем его к рабочему столу и отключаем обычным `ChangeDisplaySettingsEx` (запасной путь `SetDisplayConfig` extend), это не требует прав администратора. При старте приложения и при выходе оставшийся подключённым монитор отключается.
  - Протокол: `DisplayInvite` (хост → устройство) → `DisplayExtendRequest(w, h, масштаб)` (устройство → хост, физические пиксели основного экрана) → хост выбирает режим (точный, иначе той же формы не больше экрана, иначе ближайшей формы), при отсутствии точного один раз запускает свою копию с правами администратора (`--vdd-add-mode WxH`): добавляет `<resolution>` в XML и перезапускает устройство через SetupAPI `DIF_PROPERTYCHANGE`. Монитор ставится по стороне из раскладки, масштаб — недокументированным `DisplayConfigSetDeviceInfo` (тип -4, как у приложения «Параметры»; при неудаче остаётся выбор Windows). Дальше обычный поток монитора с видом `display`; устройство принимает его, только если само просило в последние 30 с. Отказ приходит `DisplayExtendResult` с причиной.
  - На хосте переход ввода на это устройство через край отключён (`IsCrossingSuppressed`), звук за таким «просмотром» не следует. Окно просмотра на устройстве в этом режиме сразу без рамки на весь основной экран.
  - Проверено: выбор режима, размещение, правка XML, сквозной сценарий двух узлов без драйвера (отказ с причиной). Не проверено с установленным драйвером: на машине разработки его нет.
- Синхронизация раскладки клавиатуры (`InputSharingService.KeyboardLayout`, `Keyboard/KeyboardLayouts`, `Keyboard/KeyboardLayoutFilter`), сообщение `KeyboardLayout(Layout)` в канале Control (младшие 32 бита HKL):
  - Управляющий при начале захвата (и при переходе сразу к третьему устройству) шлёт свою раскладку. Получатель подбирает установленную: та же, иначе того же языка, иначе того же базового языка. Затем шлёт `WM_INPUTLANGCHANGEREQUEST` окну с фокусом в активном потоке, как языковая панель. При стандартном режиме Windows «один способ ввода для всех окон» переключается вся сессия.
  - Горячая клавиша языка на управляющем проглатывается хуком и уходит на управляемое устройство, поэтому переключение происходит там. Управляемое устройство раз в 150 мс смотрит раскладку активного окна и сообщает управляющему о смене. `KeyboardLayoutFilter` отсекает свои переключения по чужому запросу (ожидание до 1,5 с) и смену активного окна со своей раскладкой (режим «для каждого окна»). Управляющий запоминает последнюю раскладку и включает её у себя при возврате ввода.
  - Окно просмотра шлёт раскладку своего потока при активации, при включении управления и при смене языка, с задержкой 300 мс. Горячая клавиша, нажатая в окне, уходит туда клавишами и переключает язык сама, а сообщение должно прийти после неё. Обратно источник ничего не сообщает: при разном наборе языков встречные сообщения переставили бы языки местами. В режиме второго монитора раскладка не отправляется.
  - Нет подходящей раскладки — уведомление на получателе (не чаще раза в 30 минут на язык). Окна администратора `PostMessage` отклоняют (UIPI).
  - Проверено: подбор раскладки, фильтр, кодек, чтение списка и активной раскладки на машине разработки. Не проверено вживую на двух устройствах: на машине разработки нельзя переключать язык за пользователя.
- Управление окнами администратора через отдельный процесс (начало этапа 6, принцип Windows «разные права — разным задачам»):
  - Проблема UIPI: процесс средней целостности не может слать ввод (SendInput, InjectTouchInput) в окна более высокой целостности. Раньше единственным обходом был запуск всего приложения от администратора, но тогда обычный Проводник не может перетаскивать файлы в наш процесс и COM-вызовы с виртуальными файлами не проходят.
  - Теперь вся инъекция проходит через шов `IInjectionSink` (`WinMirroring.Input/Injection`): `LocalInjectionSink` (SendInput/InjectTouchInput в этом процессе), `RemoteInjectionSink` (сериализует вызовы в канал), `InjectionRouter` (единый экземпляр, которым пользуются все `InputInjector` и `TouchInjector`; шлёт на помощника, когда тот подключён, иначе локально — потеря помощника не роняет ввод). Коды и геометрия не изменились: `InputInjector` остался политикой (учёт зажатого, `ReleaseAll`, Nudge/Wiggle), а строит `INPUT`/`POINTER_TOUCH_INFO` теперь сам сток.
  - Помощник — отдельный exe `WinMirroring.InputHost` с манифестом `highestAvailable`, рядом с приложением (публикуется в ту же папку отдельным self-contained publish). Делает только инъекцию: ни сети, ни файлов, ни UI. Приложение (средняя целостность) — сервер именованного канала (случайное имя с GUID создаётся до запуска помощника), помощник (высокая целостность) — клиент, поэтому высокий процесс пишет «вниз» и проблем с меткой целостности объекта нет.
  - Защита: канал по умолчанию доступен только текущему пользователю, имя случайно и создаётся заранее (нельзя занять заранее), одноразовый токен в рукопожатии (приложение → помощник), приложение проверяет путь образа подключившегося клиента = наш помощник. Помощник на всякий случай освобождает зажатые им клавиши/кнопки (`TrackingInjectionSink`), если канал оборвался при зажатой кнопке. Честно: это сознательно даёт вводу с других устройств доступ к окнам администратора, поэтому опция выключена по умолчанию. Настройка `InputSettings.ElevatedInjector`, галочка «Управлять окнами администратора через помощника».
  - Протокол `InjectionCodec`: длины с префиксом, опкоды MoveAbsolute/MoveRelative/Button/Wheel/Key/Unicode/TouchFrame плюс Handshake/Bye. Абсолютные координаты шлются в пикселях, нормализацию под виртуальный рабочий стол делает сток на стороне помощника (тот же сеанс/DPI).
  - Ограничение: пока права администратора запрашиваются при каждом запуске, если опция включена; автозапуск помощника без запроса (Планировщик заданий, exe в защищённой папке) — следующий шаг. Экран блокировки и UAC по-прежнему требуют службы от SYSTEM на защищённом рабочем столе.
- Аппаратный H.264 для экрана (то, что в этапе 5 осталось «следующим шагом»; JPEG-плитки остаются как fallback):
  - `WinMirroring.Screen` подключает `Vortice.MediaFoundation` 3.8.3 (MF доступен через Vortice, поэтому без ручного P/Invoke; версия совпадает с остальными Vortice-пакетами). Весь код в `Encoding/`: `VideoInterop` (GUID'ы NV12/H264, `MF_LOW_LATENCY`, `ICodecAPI` + минимальный PROPVARIANT, старт MF, поиск ключевого кадра по NAL), `Nv12Converter` (CPU BGRA↔NV12, BT.601), `H264VideoEncoder`, `H264VideoDecoder`, `VideoCodecSupport` (проба способностей, кэш на процесс).
  - Кодер — асинхронный аппаратный MFT с D3D11 device manager и потоком-насосом по событиям (см. 5.4). Декодер — синхронный Microsoft H.264 decoder MFT (CPU NV12→BGRA). Важный урок при отладке: насос нельзя завершать на любой `SharpGenException` из `GetEvent` — при старте прилетает временная не-`NO_EVENTS` ошибка, из-за которой первый вариант насоса сразу умирал и кодер не выдавал ни одного access unit'а; теперь такие ошибки лог­гируются и насос продолжает.
  - Протокол: новое сообщение канала Screen `VideoFrame=9` (frame no, w, h, флаг ключевого кадра, access unit); whole-frame `Ack=2` переиспользуется для прежнего окна в 2 кадра. Согласование едет в `DeviceCapabilitiesMessage` (`CanEncodeH264`/`CanDecodeH264`, запрос-ответ, поэтому не теряется при гонке с подпиской), `ScreenStreamMessage.Codec` ("jpeg"/"h264", по умолчанию "jpeg" — совместимо со старым пиром). Настройка `ScreenSettings.VideoCodec` (Auto/Jpeg/H264) и `VideoBitrateKbps` на вкладке «Экран».
  - Три вещи, из-за которых путь не работал по сети и которые починены при слиянии: кадры `VideoFrame` не отдавались просмотрщику (канал Screen отдавал только плиточные `Frame`); `Encode` возвращал лишь то, что успело выйти ДО поданного кадра, поэтому каждая картинка уезжала со следующим захватом, а на неподвижном экране первая не уезжала никогда (теперь `Encode` ждёт свой access unit до 100 мс, а цикл отправки досылает то, что доготовилось позже); декодер находил конец картинки только по началу следующей (теперь после каждого access unit'а дописывается access unit delimiter, NAL 9). Просмотрщик, у которого H.264 не даёт картинки (нет декодера или 3 с тишины), просит источник перейти на плитки (`ScreenCodecFallbackMessage`).
  - Проверено на ноутбуке по loopback: сквозной цикл захват→аппаратный H.264→сессия→декодирование со сравнением с прямым захватом (`ViewerReceivesTheMonitorAsVideo`), один кадр на входе даёт одну картинку на выходе (`TheFirstFrameIsAPictureWithoutASecondOne`), round-trip протокола и NV12, проба способностей. **Не проверено на двух физических устройствах**: поток между ноутбуком и планшетом, аппаратный кодер на другой модели GPU, откат на плитки вживую. GPU zero-copy (подача текстуры в кодер и `D3DImage`-презентер) — следующий шаг, сейчас путь через CPU NV12.
  - Проверено: кодек (кодирование→применение всех вызовов, кадрирование, рукопожатие), выбор локального/удалённого стока в роутере, освобождение зажатого в `TrackingInjectionSink`, совместная публикация помощника в папку приложения. Не проверено вживую: сам обход UIPI на двух устройствах (на машине разработки один экземпляр).
- Синхронизация устройств (после этапа 6):
  - Раскладка: версия изменения — это время, но всегда выше всех виденных версий, плюс id автора для одинакового разрешения ничьей на всех устройствах (`LayoutVersion`). Устройство, принявшее раскладку, пересылает её своим остальным соединениям, поэтому она доходит и туда, где автора нет; получив более старую, отвечает своей (это же лечит потерю первого сообщения сессии). Проверено тремя реальными узлами цепочкой (`LayoutRelayIntegrationTests`).
  - Мониторы для раскладки ввода: `InputMonitorsMessage` (ключ = имя дисплея, подпись, признак основного) запрос-ответом при готовности сессии и повторно при смене дисплеев; `MonitorCatalog`/`MonitorSet` в `WinMirroring.Input` дают геометрию, открытые края и привязку точки к монитору. Для показа экрана тот же список едет в `DeviceCapabilitiesMessage` и обновляется при смене дисплеев.
  - Версии устройств: `DeviceInfoMessage` запрос-ответом; `DeviceInfoService` держит версии соседей, панель их показывает.
  - Передача файлов на одно устройство мимо буфера обмена: сообщения канала Clipboard `SendFiles=9`/`SendFilesResult=10`, транспорт — тот же чанковый канал File. Отправитель закрепляет предложение в `LocalOfferStore` (иначе его вытеснят следующие копирования), получатель сам решает, забирать ли, качает в свою папку и отвечает результатом. На этом сделаны «Открыть файл на устройстве» и обновление соседа своей сборкой (zip своей папки установки, затем его же `update.ps1`) — устройству без доступа к GitHub интернет не нужен. **Открытие и установка только после подтверждения пользователем на принимающем устройстве**: сопряжённое устройство не может само ничего запустить. Проверено двумя реальными узлами (`SendFilesIntegrationTests`).
- Новый интерфейс (React в WebView2), `src/WinMirroring.Ui` + `UiBridge`/`HubUi`/`WebWindow`:

- Свободная раскладка и быстрая передача файлов:
  - Раскладка: `LayoutPlacement(DeviceId, X, Y, Monitors)` — где на общем поле лежит начало рабочего стола устройства, в пикселях; мониторы стоят вокруг него как на самом устройстве (живые размеры из `InputMonitorsMessage`, иначе запомненные в раскладке). `DeviceLayout.Across` находит монитор другого устройства, чей край встречает уходящий край (допуск 48 px) именно в точке курсора, и точку входа на той же высоте. `LayoutMessage.Placements` — новое необязательное поле; старым устройствам вместе с ним уходит сетка, выведенная из расстановки (`DeviceLayout.ToCells`). Если расстановки нет, работает прежняя сетка. Мониторы нумеруются как в Windows, по `\\.\DISPLAYn`.
  - Файлы: «пакеты» в канале File (`BundleCodec`, сообщения 3–8). Получатель называет диапазон записей предложения; `BundleSender` читает файлы (мелкие параллельно, с бюджетом памяти), упаковывает записи в блоки по 1 МБ, сжимает каждый Brotli q1 в пуле потоков и отправляет сжатым, только если вышло меньше 92 % (уже сжатые расширения не пробуются, после серии несжимаемых блоков пробуется каждый восьмой), не опережая подтверждения получателя больше чем на окно 16 МБ. `BundleReader` декодирует и подтверждает по четверти окна. `OfferDownloader` пишет мелкие файлы параллельно; `OfferPrefetcher` для Explorer запускает один пакет с первого запрошенного файла и раздаёт потоки из памяти (бюджет 96 МБ), а всё нестандартное (повтор, перемотка, обрыв) уходит на прежний поштучный `RemoteFileStream` (окно расширено до 8 × 256 КБ). Устройство старой версии на запрос пакета молчит; через 5 с получатель переходит на прежний способ для этой сессии. Замер на loopback: 4032 файла / 68 МБ — 3,8 с пакетом против 12,2 с по-старому.
  - Прогресс любого входящего переноса идёт через `TransferReports` в `ClipboardSyncService.TransferProgress`, окно показывает скорость и оставшееся время. Скачивание для `CF_HDROP` вынесено с потока, на котором его вызвал Explorer.
- Задержка трансляции (по журналу часа работы с планшета, 1.0.64):
  - UDP-путь терялся у каждого просмотра через минуту-две и не возвращался: `VideoLink` мерил тишину от последнего подтверждения, поэтому секунда неподвижного экрана считалась молчанием пути. Теперь тишина — это не меньше трёх кадров без ответа за секунду с первого из них; путь после отказа «отдыхает» (10 с, удваивается до 2 мин, сбрасывается после минуты исправной работы) и проверяется заново. Просмотрщик отвечает на каждую серию проб (не чаще раза в 400 мс), а не один раз за просмотр. Кадры, пришедшие по соединению, сдвигают очередь сборки датаграмм (`VideoReassembly.Passed`), иначе возврат на UDP выглядел бы как сотни потерянных кадров.
  - `SendWindow` сопоставляет подтверждение с кадром по номеру, а не по порядку: кадр, целиком потерянный по UDP, больше не сдвигает все замеры на кадр (ложные «опоздания» снижали битрейт) и не держит слот. Последний кадр серии, потерянный по UDP, никем не замечался до следующего изменения экрана; теперь источник на неподвижном экране шлёт целый кадр, если ответа нет дольше 100 мс (и трёх обычных задержек).
  - Просмотрщик: если следующий кадр уже в очереди, текущий декодируется без чтения в память и отрисовки (`H264VideoDecoder.DecodeInto(read: false)`), не больше двух подряд. Раньше при времени обработки чуть больше интервала кадров очередь из трёх кадров в полёте стояла постоянно — в журнале это 46–92 мс «декодирования» при 60 кадрах/с против 10–14 мс при 15.
  - Размер: `GpuNv12Converter` пробовал только два способа задать цвета, оба с «полным» диапазоном; NVIDIA выполняет это буквально и выдаёт полный диапазон (на белом отличие 19), проверка её отвергала — кадры шли через процессор и в полном размере экрана. Добавлены два способа с явным студийным диапазоном (проверка та же, сравнение с `Nv12Converter`). Для карт, которые не проходят и их, кадр уменьшает `BgraScaler` на процессоре (билинейно до половины, усреднением ниже).
  - Окно: `BitmapScalingMode` — `Linear`, пока идут кадры, `HighQuality` через 350 мс после последнего.
  - `StopSourceAsync` ждёт отправки `ScreenStop` не дольше 2 с: на умирающем соединении отправка могла не завершиться никогда, и поток оставался жить без зрителя.
  - Декодеры просмотрщика теперь принадлежат циклу декодирования и освобождаются им самим при выходе; закрытие просмотра ждёт цикл до 3 с. Раньше `DisposeAsync` освобождал декодер сразу, пока цикл мог быть внутри него: нарушение доступа, которое роняет весь процесс (сквозной тест падал так 2 раза из 36 с кодированием на карте, 0 из 25 после исправления).
  - Проверено на этом ПК (GTX 1080 Ti): модульные тесты нового, тесты GPU-конвертации (раньше здесь пропускались), сквозной поток по loopback. **Не проверено на планшете.**

Когда новый просмотр открылся, его окно перенимает состояние управления и свёрнутость, старое закрывается. - Кадр остаётся на видеокарте до экрана (1.0.67) — то, что в 5.4 значилось как «zero-copy через `D3DImage`»:
  - Было: декодер (DXVA) → видеопроцессор в BGRA → копия в staging-текстуру и `Map` (карта при этом доделывает всё, что у неё в очереди) → `byte[]` → `WriteableBitmap.WritePixels` → загрузка обратно на карту потоком отрисовки WPF. Три прохода по тем же 8 МБ на кадр 1080p.
  - Стало: видеопроцессор пишет прямо в общую текстуру (`GpuSurface`: `B8G8R8A8`, `ResourceOptionFlags.Shared`; `GpuFrameReader.TryConvertOnto`, после него `Flush`). Окно открывает её по общему дескриптору на устройстве Direct3D 9Ex (`Direct3D9Bridge`, пакет `Vortice.Direct3D9`) и отдаёт поверхность в `D3DImage.SetBackBuffer` с программным запасным путём. `D3DImage` стоит в раскладке там же, где стоял битмап, поэтому масштаб, наложения и измерение позиций не изменились.
  - Какую текстуру можно писать, решает `ScreenViewer`: окно рисует из последней подтверждённой (`Shown`) и в любой момент может перейти на выданную, но ещё не подтверждённую (`Handed`), поэтому декодер пишет в третью (`Spare`). Отсюда три текстуры на набор; с двумя на экране оказались бы верх одного кадра и низ другого. Наборов два: для кадров всего экрана и для кадров приближенной части — картинка всего экрана под частью должна оставаться прежней. Набор другого размера не освобождается сразу (одна из текстур может быть в пути к окну или на экране), а только при следующей смене.
  - Поверхности в `Direct3D9Bridge` ищутся по объекту `GpuSurface`, не по дескриптору: дескриптор освобождённой текстуры выдаётся заново, и найденная по нему поверхность была бы картинкой, которая больше не меняется.
  - Ничто из этого не обязательно: окно просит кадры на карте (`ScreenViewer.SurfacesWanted`), только если это включено в настройках (`ScreenSettings.DirectPresent`, по умолчанию да), WPF рисует аппаратно (tier 2) и есть устройство Direct3D 9; при первом же исключении при показе перестаёт просить, и следующий кадр приходит в памяти. Аккуратное масштабирование (`HighQuality`) для кадра на карте не включается — оно считается в памяти.
  - Проверено на этом ПК (GTX 1080 Ti): кадр на карте виден через Direct3D 9 теми же пикселями и непрозрачным (`SharedSurfaceTests`); настоящее окно WPF с `D3DImage` показывает его на экране, и после смены поверхности — следующий (`DirectPresentTests`, снимок с экрана); по живому потоку декодер ни разу не выдал поверхность, из которой окно уже рисует, кадры части не тронули картинку целого, а после отказа окна кадры снова приходят в памяти. **На планшете (Intel Iris Xe) не проверено.** В строке журнала «View of …» появился счётчик кадров, оставленных на карте.
