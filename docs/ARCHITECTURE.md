# WinMirroring — архитектура и план

Дата: 2026-11-07. Статус: предложение, до начала разработки.

## 1. Цель

Одно приложение на C#, которое превращает три Windows-устройства (ПК, ноутбук, планшет) в единое рабочее место:

| Фича | Что должно работать |
|---|---|
| Перенос ввода | Курсор переходит через край экрана на соседнее устройство, клавиатура следует за курсором (как Mouse Without Borders) |
| Перенос звука | Звук устройства, которым управляем, играет на устройстве, за которым сидим (та же логика «следует за фокусом ввода») |
| Файлы | Общий буфер обмена (текст, картинки, файлы) и drag & drop через край экрана |
| Экран | Окно с живым экраном другого устройства и управлением с него (в первую очередь ПК на планшете, с тачем) |
| Сеть | Только локальная сеть; пользователь выбирает интерфейсы/подсети, чтобы работало и через VPN |

Все устройства равноправны: на каждом стоит одно и то же приложение, выделенного сервера нет.

## 2. Почему не готовое

На 2026-11 ни один бесплатный продукт не закрывает все пять пунктов:

- PowerToys Mouse Without Borders: ввод + буфер + файлы через буфер (лимит ~100 МБ). Нет звука и экрана.
- Deskflow 1.27 / Input Leap: ввод + буфер. Нет файлов, звука, экрана.
- Hydra (новый, март 2026, GPL): ввод + буфер + файлы. Нет звука и экрана, не обкатан.
- Sunshine + Moonlight: экран + звук + удалённое управление, но это «стриминг игры», а не бесшовный KVM.
- Parsec: то же, закрытый, требует облачный аккаунт.
- RDP: блокирует консольную сессию, для зеркалирования не годится.

Покрыть всё можно только связкой из трёх-четырёх программ с разной логикой подключения и настроек. Поэтому пишем своё.

## 3. Стек

- .NET 10 (LTS), C# 14, TFM `net10.0-windows10.0.22621.0` (даёт проекции WinRT: Windows.Graphics.Capture и т.д.).
- UI: WPF. Причины: зрелый, лёгкий трей-апп, нормальный тач, можно хостить Direct3D-поверхность через HwndHost без лишних копий кадра. WinUI 3 красивее, но тяжелее в упаковке и отладке; переход возможен позже, ядро от UI не зависит.
- Win32 interop: `Microsoft.Windows.CsWin32` (генератор P/Invoke из метаданных, без ручных DllImport).
- Графика и медиа: `Vortice.Windows` (Direct3D11, DXGI, Media Foundation).
- Аудио: `NAudio` (WASAPI loopback/render), кодек Opus через `Concentus` (чистый C#, без нативных зависимостей).
- Сериализация управляющих сообщений: JSON (System.Text.Json) с дискриминатором типа `t` — их мало, зато читаются в логах; горячие пути (ввод, медиа) — фиксированные бинарные структуры.
- Логи: Serilog в файл с ротацией.

## 4. Сеть и безопасность

**Обнаружение.** Свой UDP-маячок (multicast + broadcast) на каждом выбранном интерфейсе. Через VPN (WireGuard, Tailscale, ZeroTier) broadcast обычно не ходит, поэтому дополнительно: ручной ввод адреса и список «запомненных» адресов пиров. Выбор интерфейсов/подсетей — отдельная настройка, слушатели биндятся только на выбранные адреса, никогда на 0.0.0.0.

**Транспорт.**

| Канал | Протокол | Зачем так |
|---|---|---|
| Управление, ввод, буфер обмена | TCP + TLS 1.3, одно мультиплексированное соединение, кадры с префиксом длины | Надёжность и порядок важнее, в LAN задержка TCP достаточна (MWB и Synergy тоже на TCP) |
| Файлы | Отдельное TCP + TLS соединение на передачу | Чтобы большой файл не блокировал ввод |
| Звук, видео | UDP, пакеты с seq/timestamp, шифрование AES-GCM ключом, выданным через TLS-канал | Потерянный кадр дешевле, чем ожидание ретрансмита |

QUIC (System.Net.Quic) рассматривался как единый транспорт, но в .NET нет API datagram, а выигрыш в LAN минимален. WebRTC — избыточен.

**Доверие.** У каждого устройства свой самоподписанный ECDSA-сертификат в хранилище CurrentUser\My (SChannel не принимает эфемерные ключи для TLS-сервера). TLS аутентифицирует только сервер; клиент доказывает свою личность уже внутри туннеля, подписывая случайный вызов сервера ключом своего сертификата (`PeerHandshake`). Сопряжение: на отвечающем устройстве показывается 6-значный PIN, на инициаторе он вводится; обе стороны обмениваются HMAC от ключа, выведенного из PIN, по обоим отпечаткам и nonce (`PairingCrypto`). После сопряжения отпечаток закрепляется (pinning), повторный ввод PIN не нужен. Непарные устройства видны в списке, но могут только запросить сопряжение.

Известное ограничение: 6-значный PIN с HMAC не защищает от активного MITM, который сидит в сети ровно в момент сопряжения и перебирает PIN офлайн. Для домашней сети это принято осознанно; в окне сопряжения показаны оба отпечатка для ручной сверки. Полноценная защита — PAKE (SPAKE2), отложена.

## 5. Модули

### 5.1 Ввод (WinMirroring.Input)

- Захват на устройстве, у которого физическая мышь/клавиатура: низкоуровневые хуки `WH_MOUSE_LL` и `WH_KEYBOARD_LL` на потоке с message loop; в «удалённом» режиме события проглатываются (возврат 1). Относительные дельты мыши берём через Raw Input (`WM_INPUT`), а не из координат курсора, чтобы не терять точность при упоре в край.
- Инъекция на принимающей стороне: `SendInput`. Клавиши передаём скан-кодами (`KEYEVENTF_SCANCODE`), чтобы не зависеть от раскладки; синхронизируем состояние модификаторов при переходе и сбрасываем их при разрыве связи.
- Раскладка устройств: пользователь расставляет устройства на 2D-сетке в UI. Края считаются по объединению прямоугольников мониторов каждого устройства (мультимонитор учитывается). Горячая клавиша «вернуть управление домой».
- Переход вместе со звуком и фокусом клавиатуры: событие `FocusChanged(deviceId)` — единая точка, на которую подписаны аудио и буфер.
- Ограничение UIPI: процесс средней целостности не может слать ввод в окна с повышенными правами (UAC, admin-приложения). Этап 1: опция «запускать с правами администратора». Позже: служба Windows + помощник в сессии пользователя (как MWB «service mode»), чтобы работали экран блокировки и UAC.

### 5.2 Звук (WinMirroring.Audio)

- Захват: WASAPI loopback с выбранного render-устройства (не обязательно default). Рендер: WASAPI shared, event-driven, буфер 10–20 мс. Джиттер-буфер на приёме с адаптивной целью 20–40 мс.
- Кодек: по умолчанию PCM 48 кГц 16 бит стерео (~1,5 Мбит/с, для LAN ничто), Opus 128–256 кбит/с для Wi-Fi/VPN. Переключается в настройках.
- Логика: «звук следует за фокусом ввода» плюс ручное закрепление («всегда гнать звук ноутбука на ПК»).
- Подводный камень: loopback берёт микс после регулятора громкости устройства, так что mute на источнике, как правило, глушит и loopback. Чтобы источник молчал локально, варианты: (а) вывод на endpoint без динамиков (HDMI монитора, S/PDIF), приложение само переключает default-устройство на время сессии и возвращает обратно; (б) process-loopback API Windows 11 (`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`, режим «все процессы кроме своего») — проверить в прототипе, зависит ли от mute; (в) виртуальный аудиокабель (драйвер ядра, на C# не пишется, только как внешняя опция).

### 5.3 Буфер обмена и файлы (WinMirroring.Clipboard, WinMirroring.Files)

- Слушатель `AddClipboardFormatListener` → `WM_CLIPBOARDUPDATE`. Текст, HTML, картинки (PNG/DIB) до настраиваемого лимита отправляются сразу; для файлов (`CF_HDROP`) уходят только метаданные.
- Вставка файлов, этап 1 (как в MWB): при `Ctrl+V` на приёмнике файлы докачиваются в локальный кэш, затем в буфер кладётся `CF_HDROP` с путями кэша. Работает везде, цена — ожидание перед вставкой.
- Вставка файлов, этап 2: виртуальные файлы через свой `IDataObject` с `CFSTR_FILEDESCRIPTORW` / `CFSTR_FILECONTENTS` и отложенным рендерингом — Explorer тянет байты по сети прямо в момент вставки.
- Drag & drop через край: на источнике при переходе с зажатой кнопкой под курсором у края появляется прозрачное окно-`IDropTarget`, оно получает перетаскиваемый `IDataObject` и список файлов; на приёмнике запускается свой `DoDragDrop` с прокси-объектом, реальные байты стримятся при drop.
- Передача файлов: чанки 256 КБ – 1 МБ, хэш на чанк, докачка, прогресс в UI, ограничение скорости по желанию.

### 5.4 Экран (WinMirroring.Screen)

- Захват: Windows.Graphics.Capture по монитору (или окну), кадр приходит как D3D11-текстура, курсор рисуется самим WGC.
- Кодирование: Media Foundation H.264 encoder MFT с аппаратным ускорением (NVENC на GTX 1650, AMD VCE, Intel QSV — все через MF), 30–60 fps, 10–30 Мбит/с в LAN, программный fallback. Текстура не покидает GPU до энкодера.
- Декодирование: MF H.264 decoder с D3D11/DXVA, вывод в swap chain внутри `HwndHost` в окне WPF — без копий через managed-память.
- Управление с планшета: тап = клик, долгое нажатие = правая кнопка, два пальца = скролл, щипок = зум окна просмотра; перо — через `InjectSyntheticPointerInput` с давлением. Ввод идёт тем же каналом, что и в 5.1, но в «абсолютных» координатах.
- Звук в этом режиме стримится тем же модулем 5.2.

### 5.5 Приложение (WinMirroring.App)

- Трей-иконка, автозапуск, окно настроек: устройства и сопряжение, раскладка на сетке, интерфейсы/подсети, звук, буфер, горячие клавиши.
- Окно просмотра экрана — отдельное, полноэкранное на планшете.
- Один процесс на устройство. Служба Windows для UAC/экрана блокировки — отдельный этап.

## 7. Этапы и критерии готовности

| Этап | Содержание | Готово, когда |
|---|---|---|
| 0 | Окружение, каркас решения, Directory.Build.props, CI-сборка `dotnet build` | Пустое приложение собирается и висит в трее |
| 1 | Ядро: обнаружение, выбор интерфейсов, сопряжение по PIN, TLS-канал, настройки | Два устройства видят друг друга, спариваются, показывают «подключено», переживают переподключение |
| 2 | Ввод: раскладка, края, хуки, SendInput, горячие клавиши, модификаторы | Управление тремя устройствами одной мышью и клавиатурой без залипаний |
| 3 | Буфер обмена: текст, картинки, файлы через кэш | Ctrl+C на одном, Ctrl+V на другом, включая файлы |
| 4 | Звук: loopback → PCM/Opus → рендер, следует за фокусом | Звук ноутбука в наушниках ПК с задержкой < 50 мс без щелчков |
| 5 | Экран: WGC + MF H.264 + тач-управление | Планшет показывает ПК при 30–60 fps с задержкой < 100 мс в LAN |
| 6 | Drag & drop через край, виртуальные файлы при вставке, служба для UAC/экрана блокировки, полировка DPI и мультимонитора | Повседневное использование без обходных путей |

Этапы 3 и 4 независимы друг от друга и от 5, их можно вести параллельно после этапа 2.

## 8. Риски и открытые вопросы

- Тихий звук на источнике без драйвера (см. 5.2) — проверяется прототипом на этапе 4.
- UAC/экран блокировки требуют службу и помощник с UIAccess; до этапа 6 ввод в такие окна не попадает.
- Аппаратный энкодер на планшете может отсутствовать — нужен программный fallback и настройка качества.
- Broadcast через VPN не ходит — ручные адреса обязательны с этапа 1.
- Антивирусы могут ругаться на глобальные хуки и SendInput; подпись сборок желательна.

## 10. Состояние

- Этапы 0–1 реализованы: `WinMirroring.Core` (обнаружение, TLS, рукопожатие, сопряжение, сессии), `WinMirroring.App` (трей, вкладки «Устройства», «Сеть», «Настройки», окна сопряжения), `wm-cli`, 40 тестов, включая интеграцию двух узлов на loopback.
- Этап 2 реализован в `WinMirroring.Input`: поток с хуками `WH_MOUSE_LL`/`WH_KEYBOARD_LL` и окном Raw Input, `InputInjector` на SendInput, бинарный кодек канала Input, раскладка-сетка с синхронизацией через `LayoutMessage`, `InputSharingService` с переходами через края в обе стороны, возвратом по Ctrl+Alt+Home и отпусканием зажатых клавиш при обрыве. В приложении вкладка «Раскладка» и индикатор «где ввод».
- Отличия от плана: движение мыши берётся из Raw Input (а не из координат хука), потому что у края экрана координаты зажаты и дельты теряются; инъекция движения абсолютная, чтобы не накладывать ускорение указателя дважды; injected-события (hDevice = 0) не считаются физическими, иначе управляемое устройство само пыталось бы перейти к соседу.
- Доработка этапа 2 по итогам проверки на устройствах (протокол v2):
  - Дёрганое движение. Причины: на управляемой стороне позиция бралась из GetCursorPos сразу после SendInput и отставала, а движение шло в сырых отсчётах мыши без ускорения. Теперь управляющий берёт смещение из `pt` низкоуровневого хука относительно припаркованного курсора (скорость и ускорение указателя уже применены), курсор паркуется в центре основного монитора под почти прозрачным окном-щитом с пустым курсором. Управляемая сторона ведёт свою позицию (`RemoteCursorPlayer`) и сверяется с системой только после 150 мс простоя.
  - Компенсация сети: каждое движение несёт метку времени управляющего в микросекундах, `PlayoutScheduler` оценивает минимальную задержку и пиковый разброс над ней и проигрывает движение с исходными интервалами на отдельном потоке с таймером высокого разрешения. Буфер адаптивный, ограничен настройкой (по умолчанию 30 мс). Клики и клавиши сначала доигрывают накопленное движение, чтобы попадать в нужную точку.
  - Блокировка ввода при обрыве. Причина: поток-обработчик ждал записи в сокет, а мёртвое соединение замечалось только через тайм-аут TCP или heartbeat. Теперь отправка идёт через буфер `InputSender` и никогда не блокирует хуки; захват — это аренда, которую управляемая сторона продлевает keepalive каждые 250 мс. Без ответа 1,5 с хук сам отпускает ввод при следующем событии. Управляемая сторона без вестей 2 с отпускает зажатые клавиши. На сокетах включены TCP keepalive и TCP_MAXRT = 10 с.
  - Приложение: контекстное меню устройства, колонка задержки, прикладной пинг (`PeerSession.PingAsync`), настройки сглаживания.
- Не проверено на двух физических устройствах после доработки.
- Следующий этап: 3 (буфер обмена).
